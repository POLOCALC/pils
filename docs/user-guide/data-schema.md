# Data Schema and Storage

All flight data in PILS follow one schema (`pils.schema`, version 1) and are
stored the same way (`pils.store`). Loaders read each file with the names of
its format; `Flight` renames the columns to the schema when it loads them.

## Column names

- `snake_case`.
- The unit is the suffix: `_deg`, `_rad`, `_m`, `_m_s`, `_m_s2`, `_deg_s`,
  `_rad_s`, `_g`, `_hpa`, `_c` (°C), `_v`, `_a`, `_mv`, `_pct`, `_rpm`, `_s`,
  `_ms`, `_us`, `_ns`, `_dbm`, `_db`, `_pw`, `_mw`. Counts, flags, states,
  quaternions and values whose unit is not known have no suffix.
  `pils.schema.unit_of("gyro_z_deg_s")` gives `"deg/s"`.
- Heights say what they are measured from: `h_ell_m` (WGS84 ellipsoid),
  `h_msl_m` (mean sea level), `h_rel_m` (take-off), `h_m` (unknown).
- `timestamp` is the time base of every table: UNIX seconds, UTC, float64.
  `datetime`, where present, is the same instant as `Datetime("us", "UTC")`.
- Tables have `snake_case` names too: `payload_data.inclinometer["ins"]`,
  `drone_data.records["imu_atti_0"]`.
- Synchronized GPS tables (`drone`, `litchi`, `reference_gps`) have the
  position as `lat_deg`, `lon_deg`, `h_ell_m`.

Columns not listed below are converted to `snake_case` (`timeOfWeek_s` →
`time_of_week_s`). The AZEL CSV handed to the telescopes keeps its own header
(`timestamp, az, el, srange`).

!!! note "Heights"
    DJI calls the RTK height `hmsl`, but it is referenced to the RTK base
    position, which the POLOCALC bases broadcast as ellipsoidal heights:
    `rtk_h_ell_m` agrees with the payload GPS ellipsoidal height within a few
    metres, and differs from its height above mean sea level by the geoid
    separation (31 m at the site). Heights above mean sea level used for the
    synchronization (DJI GPS without RTK, BlackSquare) are converted with the
    geoid separation reported by the payload receiver.

## Storage

Every product is a write-once directory per revision (see
[Directory Structure](directory-structure.md)):

```
rev_YYYYMMDD_hhmmss/
├── manifest.json        # schema version, code (pils version, git commit,
│                        # uncommitted changes), tables (rows, dtypes, units),
│                        # the run's metadata
├── <table>.parquet      # one Parquet file per table (zstd)
└── ...                  # plots, CSV of the run
```

- **Parquet** keeps the column types, nulls and time zones, and each file
  carries the units of its columns (`pils.store.read_units`). polars, pandas,
  pyarrow, DuckDB, R, Julia and MATLAB read it without PILS.
- **Write-once**: the manifest is written last; a revision with a manifest
  is complete and is never changed. A failed run leaves no partial revision.
- **Provenance**: the manifest records the git commit of the code that made
  it, and whether the code had uncommitted changes.

```python
import polars as pl
from pils import store

tables, metadata = store.load_version("proc/flight/sync", "rev_20261016_152030")
drone = tables["drone"]

# or without PILS
drone = pl.read_parquet("proc/flight/sync/rev_20261016_152030/drone.parquet")
```

Results saved in HDF5 by earlier versions are converted with
`pils migrate <flight>/proc` (the HDF5 files are kept); `Flight.from_hdf5`
still reads HDF5 flight files and renames their columns to the schema.
